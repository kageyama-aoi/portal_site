# 機能提案: 作業フローHTMLの「配布バージョン管理」

> **状況**: MVP（段階1＋2＋3-a＋3-b B-1）は実装済み（Issue #16）。
> 発行履歴は「localStorage を作業コピー＋ `data/distribution-log.json` を共有ファイル」の二層構成に変更済み（下記 §2）。
> 未実装は 段階3-b B-2/B-3、段階4、「閲覧専用で出力」オプション。

## 1. 背景と課題

作業フローは `HTML出力` で単体HTMLとして書き出し、他人へ配布できる。
本格運用を始めると、次が管理できず心苦しい、という課題が出ている。

- **どの版を配ったか分からない** — 出力HTMLに載るのは「出力日」だけ。手順を直して配り直すと、
  受領者が古い版なのか最新版なのか、配った側も受け取った側も判別できない。
- **誰にどの版を配ったか記録がない** — 配布は手動（メール・ファイル共有）で、台帳がない。
- **受領後に改変されうる** — 出力HTMLは `編集する` トグルで本文を書き換えられる。
  受領者が手元で直すと、正本からさらに乖離する。
- **何が変わったか伝わらない** — 版が変わっても変更点の説明が同梱されない。

## 2. 制約（この設計で守るもの）

- サーバー不要・ビルドなし・バニラJS（`CLAUDE.md` の制約）。
- 出力HTMLは単体で開ける（オフライン動作）ことを維持。
- データは `data/data.json` と `localStorage` のみ。
- 既存の出力レイアウト・編集/保存フローは壊さない。
- **配布物・配布手順から「Git（GitHub）で管理していること」が受領者に伝わらないこと。**
  - 出力HTMLに生成元・リポジトリ・ツール名を示す文字列を残さない。
  - 更新確認や入手先に `*.github.io` / `github.com` のURLを出さない。
  - 「検証コード」がコミットSHA（16進8桁）に見えないフォーマットにする。

> この制約により、当初案の「段階3-b: GitHub Pages にマニフェストを置く」は**そのままでは採用しない**。
> 代わりに §3 段階3-b を「ホスト非依存の更新確認」に差し替える（下記）。

## 3. 提案（4段階・上から順に導入可能）

### 段階1: 版情報をデータと出力HTMLに埋め込む【最小・基盤】

すべての土台。これだけでも「口頭で版を照合する」運用ができる。

**データモデル追加**（`Workflow` に3フィールド）

| フィールド | 型 | 説明 |
|---|---|---|
| `rev` | number | 版番号。1始まり。内容を変更して保存するたびに +1 |
| `updatedAt` | string (ISO) | 最終更新日時 |
| `contentHash` | string(8) | `steps`＋`title`＋`description` を正規化した文字列のハッシュ先頭8桁（djb2等の軽量実装で十分） |

- `WorkflowManager.updateWorkflow()` / `addStep` / `updateStep` / `deleteStep` で
  「内容が実際に変わったとき」だけ `rev` を +1 し `updatedAt` を更新、`contentHash` を再計算する。
- 旧データ（`rev` 無し）は読み込み時に `rev: 1` を補完（`_migrateLegacyPortal` と同じ発想）。

**出力HTMLへの反映**

- ヘッダー表示: `バージョン v3 ・ 2026-08-27 更新 ・ 照合コード R3-0827-KTMR`
  - 「照合コード」は **コミットSHAに見えない形式**にする。例: `R{rev}-{MMDD}-{base32を4文字}`。
    16進8桁（`a1b2c3d4`）はGit連想が強いので避ける。
- ファイル名: `作業フロー名_v3_20260827.html`（現行の `_workflow_日付` を置換）
- 機械可読メタを埋め込む（後続段階すべての足がかり）:
  ```html
  <script type="application/json" id="wf-meta">
  { "workflowId": "...", "title": "...", "rev": 3, "contentHash": "a1b2c3d4",
    "exportedAt": "2026-08-27T10:00:00+09:00", "appExportSchema": 1 }
  </script>
  ```

**運用イメージ**: 受領者が「右上の検証コード a1b2c3d4 / v3」と伝える → 配布側がアプリで照合し
「それは2版古いです」と即答できる。インフラゼロ。

### 段階2: 発行履歴（配布台帳）【配布側の記録・確定要件】

> **要件（確定）**: 「誰に配ったか」を**メモレベルで**残せること。厳密な宛先管理・CRMは不要。
> 手で1行書ける気軽さを最優先し、入力は任意（空でも出力は通す）。

**出力時の記録**

- 出力確定ダイアログに自由記述欄「**配布先メモ**」を1つ追加（例: `営業部 田中さん`、`3課 定例で共有`、`西日本 全員`）。
  - プレースホルダ: 「誰に渡すか一言（後から編集できます）」
  - 直近に入力した配布先を候補サジェスト（毎回打ち直さなくて済む）。
- 出力を実行すると、ログを1件自動追加:
  `{ id, workflowId, title, rev, 照合コード, format: 'html'|'pdf', exportedAt, recipientNote }`
- HTML/PDF どちらの出力でも記録する。

**「発行履歴」ダイアログ（新規）**

- 一覧表示: 日時 / フロー / 版 / 配布先メモ / 形式。新しい順。
- 各行の配布先メモは**後から追記・修正できる**（配ったあとに宛先が増える運用に対応）。
- 行の追加（アプリ外で配ったぶんを手入力）・削除も可。
- フロー別フィルタ、CSV／JSON書き出し。
- サマリ表示: 「このフロー 最新 v5 ／ 記録上いちばん古い配布は 田中さん(v3・2026-07-10)」。

**プライバシー配慮**: 配布先メモは個人名が入りうるので、
- CSV/JSON書き出しは明示操作でのみ。自動送信は一切しない。
- 出力HTML（配布物）には**配布先メモを絶対に含めない**（`wf-meta` にも入れない）。台帳は配布側の手元だけ。

**保存先（実装済みの構成）**

data.json と同じ「fetch で読み・download で書き」モデルを踏襲した二層構成にした。

| 層 | 役割 | 実体 |
|---|---|---|
| 作業コピー | 常時の読み書き。リロードで消えない | `localStorage['portalWorkflowDistributionLog']` |
| 共有ファイル | 同一PC内での共有・バックアップ | `data/distribution-log.json`（**.gitignore 対象**） |

- 起動時に `fetch('data/distribution-log.json')` → `applyFileData()` で localStorage へマージ取り込み。
  同一PC内なら別ブラウザ・別ポートで開いても同じ履歴が見える。ファイルが無い / `file://` でも黙って localStorage のみで動作。
- 出力で追記が起きると `hasUnsavedChanges` が立ち、「発行履歴」ボタンに ● が付く。
- 「台帳を保存」で `distribution-log.json` をダウンロード → `data/` に置き直す（data.json と同じ手作業）。
- 「読み込み」で任意の台帳 JSON を選んで **id 突き合わせマージ**（複数端末の履歴を1つに集約できる）。
- CSV 書き出しは Excel 確認用に別途用意。

理由: 個人名が入りうるので git には載せたくない（.gitignore）が、localStorage だけだとオリジン/ブラウザごとに分断され「同一PC内で共有」ができない。fetch されるファイルを1枚挟むことで両立させる。

### 段階3: 受領側での「改変検知」と「最新版チェック」【受領側の安心】

出力HTMLに埋めた `wf-meta` を使い、開いた本人が状態を判断できるようにする。

**3-a. 改変検知（インフラ不要）**

- 出力時、本文（`[data-editable]` と `.link-input`）から `contentHash` を計算し `wf-meta` に保存。
- HTMLを開くたびに現在の本文で再計算 → 一致なら「📄 正本どおり」、不一致なら
  「⚠ このファイルは受領後に編集されています」バッジ。
- 現行の「📄 原本 / 📄 複製」バッジを、この判定に統合・高精度化する。

**3-b. 「最新版へ誘導する」— ホスト非依存の3案（Git運用を露出しない）**

自動で「古い」と判定するにはネットワーク上に正解の版情報が要る。Git/Pagesを見せたくないので、
露出しない方法を弱い順に3つ。**まずは B-1 で十分**なことが多い。

**B-1｜見直し予定日 + 入手先フリーテキスト（ネットワーク不要・第一推奨）**
- 出力時に任意で設定:
  - `次回見直し予定`（例: `2026-12`）
  - `最新版の入手先`（自由記述。例: `共有フォルダ「作業手順」』 / 担当: 総務 佐藤`）
- 出力HTMLの挙動:
  - 常時: フッターに「最新版の入手先: 〜」を小さく表示。
  - 予定日を過ぎたら: 「⏰ この手順書は {予定日} に見直し予定でした。最新版を入手先にご確認ください。」
- Git は一切出てこない。「古いかどうか」は断定せず「確認して」と促すだけ。

**B-2｜配布フォルダに相対 `latest.json` を同梱（限定的なネットワーク・第二推奨）**
- 配布を「特定の共有フォルダ（社内共有ドライブ / SharePoint / Google Drive 等、受領者が普段使う場所）」経由に統一する。
- アプリに「配布フォルダ用ファイル一式を書き出し」機能を追加:
  - `作業フロー名_v3.html` 本体
  - `_flowmeta/<workflowId>.json`（`{rev, updatedAt, 照合コード, 入手手順}` だけの小さいファイル）
- 出力HTMLは開いたとき **相対パス** で `_flowmeta/<id>.json` を `fetch('./_flowmeta/...')`:
  - 同じフォルダから開かれていれば取得成功 → `rev` 比較で「🆕 新しい版があります」。
  - ローカルにコピーされて単体で開かれた場合は取得失敗 → 何も出さず B-1 の表示だけ残る。
- 絶対URLゼロ・ドメインゼロ。`file://` の相対fetchはブラウザにより制限されるため、
  「共有ドライブをWebDAV/クラウドURLで開く」運用と相性が良い（要検証）。

**B-3｜中立ドメインでの更新確認（インフラあり・任意）**
- どうしても「開くだけで最新版チェック」をしたいなら、**GitHubと分からないホスト**に置く:
  - 独自ドメイン（`flows.じぶんの会社.jp` を Pages / Netlify / Vercel にCNAME）
  - あるいはクラウドストレージの公開直リンク
- アプリの「更新確認先URL」設定に、その中立URLだけを入れる。仕組みは当初の 3-b と同じ
  （`fetch` → `rev` 比較 → バッジ）。**GitHub由来と受領者に分かるURLは設定しない**のが利用条件。
- 実装コストは B-1/B-2 と共通化できる（`rev` 比較ロジックは1つ）。

> 内部で data.json を git 管理していること自体は、上記いずれの案でも受領者に伝わらない
> （出力HTMLは元々 Git を参照していない）。露出源は「更新確認先URL」と「配布物内の文字列」だけなので、
> そこを塞げばよい。

### 段階4: 改訂履歴の同梱と、受領HTMLの差分読み込み【運用の仕上げ】

**4-a. 改訂履歴（changelog）**

- `rev` を上げるとき、任意で1行メモ（例: `freeeログイン手順を追加`）を記録。
  `Workflow.history: [{ rev, at, note }]`。
- 出力HTMLに「改訂履歴」折りたたみセクションを同梱 → 受領者が「前回からの変更点」を即把握。

**4-b. 受領HTMLの差分読み込み**

- アプリに「配布済みHTMLを読み込んで現行と比較」機能。
- 受領者から送られた古いHTMLをドロップ → `wf-meta` ＋本文からステップを復元 → 現行版とステップ単位でdiff表示。
- サポート用途（「あなたのファイル送って→どこが古いか教えます」）に有効。

## 4. 推奨するMVP

| 優先 | 内容 | 目安 | Git露出 |
|---|---|---|---|
| ★1 | 段階1（版情報＋メタ埋め込み＋照合コード＋ファイル名） | 小。data.json＋workflowManager＋出力HTML | なし |
| ★2 | 段階2（発行履歴＝配布先メモ / localStorage＋CSV） | 中。ダイアログ1つ新規 | なし（配布側のみ） |
| ★3 | 段階3-a（改変検知バッジ） | 小〜中。既存バッジの置換 | なし |
| ★4 | 段階3-b B-1（見直し予定日＋入手先フリーテキスト） | 小。出力設定に2項目 | なし |
| ☆5 | 段階3-b B-2（相対 latest.json） | 中。配布フォルダ書き出し機能 | なし |
| ☆6 | 段階4（改訂履歴・差分読み込み） | 中。運用が回り始めてから | なし |

**段階1＋2＋3-a＋3-b(B-1)** で「配った版が特定でき／台帳があり／改変が分かり／入手先が伝わる」状態になる。
すべてネットワーク不要・Git非露出。B-2 は配布をフォルダ経由に統一できるなら追加すると良い。
B-3（中立ドメインでの自動チェック）は独自ドメインを用意する気があるときだけ。

## 5. 「Git運用を露出させない」ためのチェックリスト

- [ ] 出力HTMLの内容（コメント・`<meta generator>`・`<title>`・`wf-meta`）にリポジトリ名/ツール名/`github` を含めない。
- [ ] `wf-meta` の `workflowId` は内部IDのまま（`link_...` 形式）で問題ないが、URLやパスは入れない。
- [ ] 照合コードは16進8桁を避ける（コミットSHA連想を防ぐ）。`R3-0827-KTMR` 形式。
- [ ] 「更新確認先URL」設定にプレースホルダやサンプルで `github.io` を出さない。
- [ ] README / 配布時の案内文でも「GitHubで管理」に触れない。
- [ ] （B-2採用時）同梱フォルダ名は `_flowmeta` など中立な名前。`.git` 由来を思わせない。

## 6. 補助オプション（MVPと独立して有効）

- **「閲覧専用で出力」オプション** — `編集する` トグルごと出力から外すモード。
  配布物を確実に不変にでき、乖離の芽を断てる。編集機能は配布側の自分用イテレーションでのみ使う。
- **出力ファイル名テンプレートの設定** — `{title}_{rev}_{date}` などをユーザーが調整可能に。
