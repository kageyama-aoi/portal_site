portal_site 技術ポイント集

1. 全体像 — このコードから何を学ぶか

portal_site はフレームワーク・バンドラーを一切使わない「バニラJS」の サーバーレスWebアプリ（リンク集ポータル）です。React/Vueのような大がかりな道具がない分、 「素のブラウザAPIとJSの言語機能だけで、どう設計を成立させるか」という判断が コードの随所にそのまま残っています。これは実務でフレームワークを使う場合でも土台になる考え方です。

  • モジュール間の依存を「関数の呼び出し」だけで管理する設計（DI・コールバック）
  • ブラウザのセキュリティ制約（ファイル書き込み不可）を回避する永続化テクニック
  • 外部ライブラリなしでの状態管理・UIコンポーネント・ドラッグ&ドロップの実装
  • 「配布先の環境に何も入っていない」前提でのHTML自己完結生成テクニック
  • DOM生成コードをテストする際のモック・検証テクニック（Jest + JSDOM）
フレームワークが裏で自動的にやってくれること（状態管理・再描画・モジュール解決）を、 このコードは全部「自分の手で」書いている。だからこそ、フレームワークが何を解決しているのかが 逆に見えてくる。以降、10個の技術ポイントとして拾っていく。

2. 技術ポイント①: 依存性注入（DI）を1箇所に集約する — app.js

このアプリには「グローバル変数」も「Reduxのようなストア」もありません。代わりに、 起動処理を1つの DOMContentLoaded ハンドラの中で全マネージャ・全ダイアログを 生成し、必要なものをコンストラクタ引数として手渡す「配線図」を作っています。 

const searchManager = new SearchManager(dataManager);
const tagManager = new TagManager(dataManager);
const linkDialog = new LinkDialog(dataManager, () => uiRenderCallback(), iconPickerDialog, configManager, searchManager, tagManager);
ui = new UI(dataManager, configManager, linkDialog, bulkLinkDialog);
ui.searchManager = searchManager;
ui.tagManager = tagManager;

js/app.js: 86〜113行目あたり

  • 各クラスは「自分が使うもの」だけをコンストラクタで受け取り、自分でnewしない（＝差し替え・テストがしやすい）
  • 生成順序に意味がある。searchManager / tagManager は linkDialog より先に作る、という順序制約がコメントで明記されている
DIの本質は「フレームワークの機能」ではなく、「あるオブジェクトが必要とするものを、 自分で作らず外から渡してもらう」という設計原則そのもの。この原則さえ守れば、 フレームワークが無くても、new を並べるだけでテスト可能な疎結合構造が作れる。

3. 技術ポイント②: コールバックによるモジュール間通信（DOMイベントを使わない）

CLAUDE.md にも明記された設計方針として、モジュール間の通知は CustomEvent のようなDOMイベントではなく、「コールバック関数をプロパティに代入する」 素朴な方法で行われています。 

// app.js: DataManager にコールバックを渡す
const onDirtyCallback = () => {
  if (ui) ui.updateSaveButtonState(true);
};
const dataManager = new DataManager(onDirtyCallback);

// dataManager.js: 変更があった箇所で呼び出すだけ
markAsDirty() {
  this.hasUnsavedChanges = true;
  if (this.onDirty) this.onDirty();
}

js/app.js: 58〜68行目 / js/dataManager.js: 70〜75行目

DOMイベントは「誰が発火して誰が受け取るか」が実行時までコード上で追いにくくなる （addEventListener がどこにあるか探す必要がある）。コールバックなら Ctrl+クリックで定義元にそのまま飛べる。DOMに関係しない純粋なロジック同士の通信では、 こちらの方が追跡性が高い。
ただしコールバックは1対1通信に向く設計。1つの変更を複数の相手に知らせたい「1対多」の通知には、 このアプリでも distributionLog.onDirtyChange のように個別プロパティを増やして対応している （本格的なPub/Subが必要になったらイベントバスへの切り替えを検討すべき規模）。

4. 技術ポイント③: JSON.parse(JSON.stringify()) でカプセル化する

DataManager.getData() は内部配列 this.data をそのまま返さず、 シリアライズ→デシリアライズしたコピーを返します。 

getData() {
  return JSON.parse(JSON.stringify(this.data));
}

js/dataManager.js: 54〜56行目

呼び出し側が返り値の配列やオブジェクトを直接書き換えても、DataManager 内部の 「正本」データには影響しない。structuredClone等より遅いが、Dateやundefinedを含まない プレーンなJSONデータ（このアプリの link/workflow オブジェクトはまさにそれ）を前提にするなら、 追加ライブラリなしで確実にディープコピーできる手軽な方法として十分実用的。
Date オブジェクトや undefined を含むデータをこの方法でコピーすると、 文字列化・欠落など意図しない変換が起きる。このアプリが日時を常に ISO 文字列 （updatedAt: "2026-08-27T..."）で持っているのは、この制約と整合させるため。

5. 技術ポイント④: Blob + createObjectURL によるファイル保存（サーバー不要の永続化）

ブラウザはセキュリティ上、JSからローカルファイルへ直接書き込めません。そこで「メモリ上に 仮想ファイルを作り、隠しリンクを自動クリックさせてダウンロードを起こす」という手法で 「保存」を実現しています。 

save(portalId = 'default') {
  const dataStr = JSON.stringify({ portals: this.allPortals, ... }, null, 2);
  const blob = new Blob([dataStr], { type: 'application/json' });
  const url = URL.createObjectURL(blob);

  const a = document.createElement('a');
  a.href = url;
  a.download = 'data.json';
  document.body.appendChild(a);
  a.click();
  document.body.removeChild(a);
  URL.revokeObjectURL(url); // メモリリーク防止
  this.markAsClean();
}

js/dataManager.js: 287〜302行目

ユーザーは保存後に「ダウンロードされた data.json を元の場所に上書き」する一手間が必要になるが、 その代わりバックエンドもDBも不要になる。「Gitでバージョン管理したいデータ」との相性も良い （CLAUDE.mdが述べる「ローカルファースト & Gitフレンドリー」の裏にある技術選択）。
URL.createObjectURL() で作ったURLは明示的に revokeObjectURL() しないと ブラウザがメモリ上に保持し続ける。ダウンロードが終わった直後に解放している点を見落とさないこと。

6. 技術ポイント⑤: 読み込み時の「後方互換マイグレーション」パターン

データ形式を将来変えても、古い形式のファイルを読み込んだ瞬間に自動で新形式へ変換し、 アプリ側は常に「最新形式しか存在しない」前提でコードを書けるようにしています。 

_migrateLegacyPortal(portalArray) {
  const hasLegacyCategory = portalArray.some(entry => entry && Array.isArray(entry.links));
  if (!hasLegacyCategory) return { data: portalArray, migrated: false };

  const flatLinks = portalArray.flatMap(entry => {
    if (entry && Array.isArray(entry.links)) {
      return entry.links.map(link => ({
        ...link,
        tags: Array.from(new Set([...(link.tags || []), entry.title]))
      }));
    }
    return entry ? [entry] : [];
  });
  return { data: flatLinks, migrated: true };
}

js/dataManager.js: 125〜146行目

  • 旧形式（カテゴリでネストしたリンク配列）と新形式（フラット＋タグ配列）が混在していても、 要素ごとに個別判定することで正しく変換する（配列の先頭だけで判定すると事故る、という 過去の失敗がコメントに残っている）
  • workflowVersion.js の ensureVersionFields() も同じ発想で、 旧データに rev フィールドが無ければ 1 を補う
マイグレーションを「起動時に一度だけ静かに変換する」形にすることで、アプリ本体のロジックは データ形式が1種類しかないという前提のまま書け続けられる。互換コードを本体ロジックの あちこちに分散させない、という規律が保たれている。

7. 技術ポイント⑥: CSS変数 + data-theme 属性 + FOUC対策

ライト/ダークテーマの切り替えは、CSSカスタムプロパティ（:root と [data-theme="dark"]）の値をJSで切り替えるだけで実現しています。 さらに「ページが表示された瞬間に一瞬ライト画面がちらつく」問題（FOUC）を、 CSS読み込み前に実行される小さなインラインスクリプトで防いでいます。 

<!-- index.html の <head> 先頭、CSSリンクより前 -->
<script>
  (function () {
    var saved = localStorage.getItem('portalTheme');
    var theme = saved || (window.matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light');
    document.documentElement.setAttribute('data-theme', theme);
  })();
</script>
<link rel="stylesheet" href="style.css">

index.html: 8〜19行目 / js/themeManager.js: 44〜53行目

「保存済みの好み → OSの設定（prefers-color-scheme） → デフォルト」という優先順位のフォールバックは、 ユーザー設定を尊重するUIの定石。CSSより前にJSで属性を確定させる、という順序がFOUC対策の肝。
localStorage はプライベートブラウジング等で例外を投げることがあるため、 try/catch で握りつぶして「表示だけは継続する」フォールバックを必ず入れている （js/themeManager.js の toggle() 内も同様）。

8. 技術ポイント⑦: 純粋関数として分離した「内容ハッシュ」と版管理 — workflowVersion.js

「作業フローの内容が変わったら版番号(rev)を上げる」「配布後に改変されたか検知する」機能は、 DOM・localStorage・fetch に一切依存しない純粋関数だけのモジュールに切り出されています。 

function djb2(str) { // 暗号用途ではない軽量ハッシュ
  let h = 5381;
  for (let i = 0; i < str.length; i++) {
    h = (((h << 5) + h) + str.charCodeAt(i)) >>> 0;
  }
  return h >>> 0;
}

export function bumpRevIfContentChanged(wf, nowIso) {
  const newHash = workflowContentHash(wf);
  if (newHash === wf.contentHash) return false; // 内容が同じなら版は上げない
  wf.rev += 1;
  wf.contentHash = newHash;
  wf.updatedAt = nowIso || new Date().toISOString();
  return true;
}

js/workflowVersion.js: 14〜20行目 / 120〜135行目

「内容が変わったか」を判定する対象は title / description / steps だけで、tags や freq は含めない（ normalizeWorkflowContent()）。「何を版として数えるか」というビジネスルールを、 まずデータの正規化関数として明文化している点が学びどころ。
そして純粋関数に分離したことで、test/workflowVersion.test.js が DOMもモックも一切使わずに検証できている。

10. 技術ポイント⑨: 外部ライブラリなしの <dialog>・<details>・ドラッグ&ドロップ

モーダルは <dialog>.showModal()、アコーディオンは <details> というHTML5標準要素をそのまま使い、並べ替えは draggable 属性と dragstart/dragover/drop イベントだけで実装しています。 

//

const card = document.createElement('details');
card.open = this.expandedWorkflowIds.has(wf.id);
card.addEventListener('toggle', () => {
  if (card.open) this.expandedWorkflowIds.add(wf.id);
  else this.expandedWorkflowIds.delete(wf.id);
});

// ドラッグ中の要素を、マウス位置に応じて挿し替える
btn.addEventListener('dragover', e => {
  e.preventDefault(); // これが無いとdropが発火しない
  const rect = btn.getBoundingClientRect();
  const after = e.clientX > rect.left + rect.width / 2;
  group.insertBefore(dragging, after ? btn.nextSibling : btn);
});

ブラウザ標準の <dialog>/<details> はフォーカストラップや アクセシビリティの基本を勝手にやってくれる。「独自実装する前に、まず標準要素で足りないか確認する」 という判断が、コード量と保守コストを両方下げている。
ドラッグ&ドロップは dragover で必ず e.preventDefault() を呼ばないと drop イベントがそもそも発火しない。素のDOM APIのドラッグ&ドロップで最初にハマりやすい点。

11. 技術ポイント⑩: 「配布先に何も入っていない」前提の自己完結HTML生成

作業フローをHTMLとして書き出す workflowExporter.js は、生成する側は ESモジュールをフルに使えるが、生成されるHTML自身はESモジュールを import できない （単体で開かれる前提のため）という制約を抱えています。この制約への向き合い方が学びどころです。 

// util/clipboard.js（アプリ本体用）とほぼ同じロジックを、
// 出力HTML用に import なしで再実装している（workflowExporter.js 内の文字列テンプレート）
function wfFallbackCopy(text, done) {
  var ta = document.createElement('textarea');
  ta.value = text;
  ta.style.position = 'fixed';
  ta.style.opacity = '0';
  document.body.appendChild(ta);
  ta.select();
  var ok = false;
  try { ok = document.execCommand('copy'); } catch (e) { ok = false; }
  document.body.removeChild(ta);
  done(ok);
}
