手を動かす ④-a': 「なぜ taro.name と書く必要があるのか」を実験する

当然の疑問として「hello は name と同じオブジェクトの中に 書いてあるんだから、わざわざ taro.name と書かずに、ただの name で通じるのでは？」と思うはずです。実際に試してみましょう。 


const taro3 = {
  name: '太郎',
  hello: function () {
    console.log('私は' + name + 'です'); // わざと taro3.name ではなく name だけを書く
  }
};

taro3.hello();

実行結果イメージ（ブラウザのコンソールで実行した場合）：

私はです
「太郎」が消えました。 しかもエラーにすらなりません。理由はこうです： オブジェクトを { } で書いても、JavaScriptは「この中に書いた関数からは、 兄弟キーの値がそのまま見える」というルールを用意していません。hello の中の ただの name は、taro3 の中の name とは無関係の、 どこか別の場所にある name という変数を探しに行きます。

たまたまブラウザには window.name（タブ名を覚えておくための、空文字の変数）が 最初から存在するため、探した先でそれが見つかり、エラーにならずに空文字 '' が 使われてしまいます。「たまたま動くが、値は空っぽ」という一番怖いバグの形です。

つまり hello の中から「このオブジェクト自身が持っている name」を取るには、 そのオブジェクト自身を、名前で明示的に指定するしかありません。 それが taro3.name のように書く理由です。

手を動かす ④-a'': そもそも「見える/見えない」を決めているのは何か

「動いた（動かなかった）のは分かったけど、なんで？」に答えるには、もう1段深く見る必要があります。 JavaScriptが「その変数が見えるかどうか」を決める基準は、たった1つです： そのコードが、どの関数（または { } ブロック）の中に、実際に書かれているか。 これだけです。オブジェクトの中かどうかは、実は関係ありません。見比べてみましょう。 


// ケースA: 関数の中に、さらに関数を書く（入れ子）
function outer() {
  let message = 'outerの変数';
  function inner() {
    console.log(message); // innerは outer の { } の"内側に書かれている"ので見える
  }
  inner();
}
outer();

// ケースB: オブジェクトの中に、関数を"値として"入れる
const obj = {
  message: 'objの中のmessage',
  inner: function () {
    console.log(message); // このinnerは obj の"内側に書かれている"わけではない。
                           // objの1つのキーの"値"として、この関数が置かれているだけ
  }
};
obj.inner();

実行結果イメージ：

outerの変数 Uncaught ReferenceError: message is not defined

同じ「関数の中に関数がある」ように見えても、A（関数の入れ子）とB（オブジェクトの値）では 矢印の意味が違います。Aは本当に内側に書かれているので下まで見えるが、Bは 「objの隣に置かれているだけ」で内側に書かれてはいないので、途中で切れています。

ここが核心です。 ケースAとケースBは見た目がよく似ていますが、 { }の意味が全く違います。

ケースAの{ }は「関数の中身」を囲む{ }です。innerという関数は、 outerという関数の{ }の内側に文字として書かれているので、 outerのmessageが見えます（これを「スコープ」と呼びます。 「コードの見た目の入れ子構造」だけで決まる、という点が重要です）。

ケースBの{ }は「オブジェクトのデータ」を囲む{ }です。 inner: function() {...}という書き方は、たまたま見た目がobjのそばにありますが、 「この関数がどこに書かれているか」というスコープの意味では、 objの外（スクリプトの一番外側）に書かれているのとまったく同じ扱いです。 だからobjのmessageは見えません。

つまり{ }には、「関数の中身を囲み、スコープを作る{ }」と 「ただのデータをまとめるだけの、スコープを作らない{ }」の2種類があり、 見た目が同じなので混同しやすいだけで、役割は無関係です。 ④-aでtaro.nameと書かないと通じなかったのは、まさにこれが理由でした。
では「オブジェクトに紐づいた関数（メソッド）が、後から自分の持ち主を知りたい」場合は どうすればいいのでしょうか。スコープの仕組みでは解決できないので、JavaScriptは 「呼び出され方に応じて中身が変わる、専用の特別な言葉」を別に用意しました。 それが次の this です。

手を動かす ④-b: this = 「今の自分自身」を指す言葉


const taro2 = {

  hello: function () {
    console.log('私は' + this.name + 'です'); // "taro2"と書く代わりに this と書く
  }
};

taro2.hello(); // taro2.hello() として呼ばれたので、このthisは taro2 自身になる

スコープ（④-a''）は「コードがどこに書かれているか」だけで決まり、実行のたびに変わることは ありませんでした。this はその逆で、同じ1つの関数でも、 「ドットの前が誰か」によって毎回中身が変わります。この「書かれた場所」ではなく 「呼ばれ方」で決まる、という点がスコープとの一番の違いです。

this は「今そのメソッドを呼び出したオブジェクト自身」に自動的に置き換わる特別な言葉です。 これのおかげで、④-aのように名前を直書きしてコピペミスする心配がなくなります。 「this = 呼び出し方によって中身が変わる箱」とだけ、まず覚えてください。

手を動かす ④-c: class = 「たい焼きの型」、constructor = 「型に生地を流し込む作業」

④-aでは「同じ形のオブジェクトを作る」のを手作業（コピペ）でやっていました。 class は、この「同じ形のオブジェクトを作る作業」そのものを自動化する道具です。 たい焼きに例えると：class は「型」、constructor は 「型に生地(データ)を流し込む作業」、new は 「型を1回使って、たい焼きを1個作る」ことに対応します。 


class Taiyaki {                 // ← "型"を1つ定義する（これから何個でも同じ形で作れる）
  constructor(filling) {        // ← new した瞬間に、その1個分だけ実行される
    this.filling = filling;     // ← 「今作っているこのたい焼き」に、中身の味を覚えさせる
  }
  taste() {                     // ← 完成したたい焼きが持っている「動作」
    console.log(this.filling + '味のたい焼きです');
  }
}

const taiyaki1 = new Taiyaki('あんこ');     // 型(Taiyaki)を使って1個目を作る
const taiyaki2 = new Taiyaki('カスタード'); // 同じ型を使って2個目を作る。中身だけ違う

taiyaki1.taste();
taiyaki2.taste();

実行結果イメージ：

あんこ味のたい焼きです カスタード味のたい焼きです

このアプリの DataManager や UI も、まさにこの class の形で書かれています。new DataManager(...) は 「Taiyakiの型からたい焼きを1個作ったのと同じように、 DataManagerという型から、実際に使う1つの実物を作る」という意味です。

Lab 1. モジュール同士を「電話番号を教える」ようにつなぐ（DI・コールバック）

これは何？
「DI（依存性注入）」と聞くと難しそうですが、やっていることは 「Aさんが必要な道具を、Aさん自身に作らせず、外の人が渡してあげる」というだけのことです。 「コールバック」は「用事が済んだら電話して」と、実行してほしい関数を先に渡しておくことです。

手を動かす


// lab1.js（ブラウザのコンソールに貼り付け）

// ❌ もしこう書いたら、Notifier は「保存する」という具体的な処理まで自分で知る必要がある
class BadNotifier {
  save() {
    console.log('データベースに保存しました'); // 保存方法をNotifierが決めてしまっている
  }
}

// ✅ 「保存が終わったら呼んでね」という関数(コールバック)を外から受け取るだけにする
class Notifier {
  constructor(onSaved) {
    this.onSaved = onSaved; // "電話番号"を受け取って覚えておくだけ
  }
  save() {
    console.log('保存処理をした（つもり）...');
    this.onSaved(); // 用事が済んだので電話をかける
  }
}

// 「保存できたら何をするか」は呼び出す側が自由に決められる
const notifier = new Notifier(() => {
  console.log('画面に「保存しました！」と表示する処理をここに書く');
});
notifier.save();

実行結果イメージ：

保存処理をした（つもり）... 画面に「保存しました！」と表示する処理をここに書く
なぜ大事？
Notifier クラスは「画面に何を表示するか」を一切知らずに済んでいます。 これにより Notifier は保存の仕組みだけに専念でき、表示方法を後から変えても Notifier 自体を書き直す必要がありません。この「知らなくていいことを増やす」考え方は、 どんな言語・どんな規模のコードでも使える最重要の設計原則の1つです。

発展：試してみよう

  • onSaved を呼ぶ前に、わざと1秒待つ（setTimeoutを使う）ように変えてみましょう。 呼び出し側のコードは1文字も変えずに動くはずです。
本物のコードではここ: js/app.js の onDirtyCallback （58〜68行目あたり）と、それを受け取る js/dataManager.js の markAsDirty()（70〜75行目）。
上級編は「技術ポイント①②: DI・コールバックによるモジュール間通信」に対応。

Lab 2. コピーを「文字列に変換して戻す」ことで完全に切り離す（ディープクローン）

これは何？
JavaScriptの配列やオブジェクトを別の変数に代入しても、実は「同じ実体」を指しているだけで、 コピーではありません（これを「参照」と呼びます）。うっかり書き換えてしまう事故を防ぐには、 完全に独立した「別の実体」を作る必要があります。

手を動かす


// lab2.js

const original = { title: '元のデータ', tags: ['work'] };

// ❌ これはコピーではない。同じ実体を指す別の名前がついただけ
const notACopy = original;
notACopy.title = '書き換えられた！';
console.log('original.title:', original.title); // ここも変わってしまう

// ✅ 文字列化して読み直すことで、完全に別の実体を作る
const original2 = { title: '元のデータ', tags: ['work'] };
const realCopy = JSON.parse(JSON.stringify(original2));
realCopy.title = '安全に書き換えた';
console.log('original2.title:', original2.title); // こちらは変わらない
console.log('realCopy.title:', realCopy.title);

実行結果イメージ：

original.title: 書き換えられた！ original2.title: 元のデータ realCopy.title: 安全に書き換えた
なぜ大事？
「データを管理するクラス」を作るとき、外部に渡したコピーをうっかり誰かが書き換えても、 管理しているクラス内部の「正しいデータ」は絶対に影響を受けない、と保証できます。 バグの原因調査で「なぜかデータが勝手に変わっている」という現象の多くは、この参照の混同が原因です。

発展：試してみよう

本物のコードではここ: js/dataManager.js の getData()（54〜56行目）。 外部に渡す配列を毎回この方法でコピーしています。

Lab 3. ブラウザに「ファイルとして保存させる」（Blob）

これは何？
JavaScriptはセキュリティ上、あなたのPCのファイルに直接書き込むことができません。 その代わりに「これはファイルの中身です」というデータ（Blob）を作り、 ブラウザに「ダウンロードしてください」とお願いする、という回り道をします。

手を動かす


// lab3.html として保存して、ブラウザで開いてから実行するか、
// コンソールに貼り付けて実行してください（ダウンロードが1つ発生します）

function saveAsFile(text, filename) {
  const blob = new Blob([text], { type: 'text/plain' }); // メモリ上に「仮想ファイル」を作る
  const url = URL.createObjectURL(blob);                 // その仮想ファイルへの一時URLを発行

  const a = document.createElement('a'); // リンクタグを一時的に作る
  a.href = url;
  a.download = filename;                 // download属性があると「開く」ではなく「保存」になる
  document.body.appendChild(a);
  a.click();                             // JSでクリックを"自動実行"させる
  document.body.removeChild(a);
  URL.revokeObjectURL(url);              // 一時URLを解放してメモリを片付ける
}

saveAsFile('こんにちは、これは保存されたファイルです。', 'hello.txt');

実行結果イメージ：

（コンソールに出力はないが、hello.txt のダウンロードが始まる）
なぜ大事？
サーバーもデータベースも無いWebページから「保存」機能を提供する、唯一と言っていい標準手段です。 設定ファイルのエクスポート・CSV出力・レポート生成など、あらゆる「ブラウザだけでファイルを作る」 場面で応用できます。

発展：試してみよう

  • type: 'text/plain' を type: 'application/json' に変え、 text の内容を JSON.stringify({hello: 'world'}) にして、 JSONファイルとして保存されることを確認してみましょう。
本物のコードではここ: js/dataManager.js の save()（287〜302行目）。 まさに同じ手順で data.json をダウンロードさせています。
上級編は「技術ポイント④: Blob + createObjectURL によるファイル保存」に対応。

Lab 4. 「次に開いたときも覚えている」を作る（localStorage）

これは何？
ブラウザには localStorage という、ページを閉じても消えない小さな保管庫が 標準で用意されています。「文字列のキーと文字列の値」のペアしか保存できない点に注意が必要です。

手を動かす


// lab4.js（コンソールに貼り付け。1回目と2回目で結果が変わることを確認する）

const KEY = 'myFavoriteColor';

function applyTheme() {
  const saved = localStorage.getItem(KEY); // 前回保存した値を読む（無ければ null）
  const color = saved || 'blue';           // 無ければデフォルト値を使う
  console.log('現在のテーマ色:', color);
  return color;
}

function setTheme(color) {
  localStorage.setItem(KEY, color); // 文字列として保存する
  console.log('保存しました:', color);
}

applyTheme();       // 1回目は「blue」（デフォルト）のはず
setTheme('green');  // 保存する
applyTheme();       // もう一度読むと「green」になっているはず

実行結果イメージ：

Lab 5. 「内容が変わったか」を自分の手で判定する（簡易ハッシュ）

これは何？
2つの長い文章が「まったく同じか」を毎回全文比較するのは大変です。かわりに、 文章から短い「指紋」のような数字（ハッシュ値）を作り、その指紋同士を比較すれば 高速に「変わったかどうか」が分かります。

手を動かす


// lab5.js

// djb2という有名な軽量ハッシュ関数（暗号用途ではなく「指紋」用）
function djb2(str) {
  let h = 5381;
  for (let i = 0; i < str.length; i++) {
    h = (((h << 5) + h) + str.charCodeAt(i)) >>> 0; // >>>0 は「符号なし32bit整数にする」おまじない
  }
  return h >>> 0;
}

const textA = 'こんにちは';
const textB = 'こんにちは';
const textC = 'さようなら';

console.log('A の指紋:', djb2(textA));
console.log('B の指紋:', djb2(textB), '← Aと同じ文章なので同じ指紋になる');
console.log('C の指紋:', djb2(textC), '← 違う文章なので違う指紋になる');

// 「内容が変わったら版番号を上げる」の最小版
function bumpVersionIfChanged(oldHash, newText, currentVersion) {
  const newHash = djb2(newText);
  if (newHash === oldHash) {
    return { changed: false, version: currentVersion, hash: oldHash };
  }
  return { changed: true, version: currentVersion + 1, hash: newHash };
}

let state = { version: 1, hash: djb2('最初の内容') };
console.log(bumpVersionIfChanged(state.hash, '最初の内容', state.version));   // 変わっていない
console.log(bumpVersionIfChanged(state.hash, '編集後の内容', state.version)); // 変わった→version+1

実行結果イメージ：

A の指紋: 1234567890 B の指紋: 1234567890 ← Aと同じ文章なので同じ指紋になる C の指紋: 987654321 ← 違う文章なので違う指紋になる { changed: false, version: 1, hash: ... } { changed: true, version: 2, hash: ... }
なぜ大事？
「内容が変わったら版番号を上げる」「配布後に改変されていないか検知する」といった機能は、 すべて「今の指紋」と「前回の指紋」を比較するだけの単純な仕組みで実現できます。 このアプリの作業フロー版管理・改変検知は、まさにこの考え方を土台にしています。

本物のコードではここ: js/workflowVersion.js の djb2()（14〜20行目）と bumpRevIfContentChanged()（120〜135行目）。

Lab 7. マウスで並び替える（ドラッグ&ドロップの最小構成）

これは何？
ライブラリを使わずマウスで要素を並び替える機能は、4つのイベント （dragstart / dragover / drop / dragend）の 組み合わせだけで作れます。最初は少し複雑に見えますが、役割はそれぞれ単純です。

手を動かす


<!-- lab7.html として保存してブラウザで開く。3つの箱をドラッグで入れ替えられる -->
<!DOCTYPE html>
<html>
<body>
  <div id="list" style="display:flex; gap:8px;">
    <div class="item" draggable="true" style="padding:20px;background:#eef;">A</div>
    <div class="item" draggable="true" style="padding:20px;background:#efe;">B</div>
    <div class="item" draggable="true" style="padding:20px;background:#fee;">C</div>
  </div>
  <script>
    let dragging = null;
    document.querySelectorAll('.item').forEach(item => {
      item.addEventListener('dragstart', () => { dragging = item; }); // 「今どれを持っているか」を覚える
      item.addEventListener('dragover', e => {
        e.preventDefault(); // これを書かないと drop が発火しない（ブラウザの初期動作がドロップ禁止のため）
        if (dragging && dragging !== item) {
          item.parentNode.insertBefore(dragging, item); // 持っている要素を、今カーソルがある位置の前に移す
        }
      });
      item.addEventListener('dragend', () => { dragging = null; }); // 持ち物を手放す
    });
  </script>
</body>
</html>

実行結果イメージ：

（A/B/Cの箱をドラッグすると、順番が入れ替わる）
なぜ大事？
ドラッグ&ドロップ用のライブラリを入れなくても、この4イベントの役割 「①持ち始めた ②今どこにいる ③離した ④持つのをやめた」を覚えておけば、 ほとんどの並び替えUIは自作できます。
ハマりどころ: dragover で e.preventDefault() を 書き忘れると、dropイベントが一切発生しません（ブラウザの初期動作は 「ドロップ禁止」だからです）。動かないときは、まずここを確認してください。

発展：試してみよう

  • 並び替えた後の順番を localStorage に保存し、ページを再読み込みしても 順番が復元されるようにしてみましょう（Lab 4 の知識と組み合わせます）。
本物のコードではここ: js/ui.js の _initViewBtnOrder() （152〜188行目）。表示切替ボタンの並び替え＋localStorageへの保存を、 まさにこの4イベントで実装しています。
